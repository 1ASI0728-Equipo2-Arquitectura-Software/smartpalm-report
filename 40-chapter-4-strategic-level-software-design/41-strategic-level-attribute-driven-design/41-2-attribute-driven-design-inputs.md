### 4.1.2. Attribute-Driven Design Inputs

Los inputs de ADD fueron consolidados a partir del problema de monitoreo agronómico, los segmentos objetivo, las User Stories y Technical Stories del capítulo III, los bounded contexts candidatos y las restricciones del trabajo final. Se seleccionaron únicamente los elementos que cambian la forma de la arquitectura: flujos que atraviesan varios contextos, operación offline, seguridad, integraciones externas, procesamiento de telemetría y despliegue independiente.

#### 4.1.2.2. Quality Attribute Scenarios

La primera versión de escenarios concentra los atributos con mayor efecto sobre la arquitectura: disponibilidad en campo, rendimiento, confiabilidad, seguridad, escalabilidad, modificabilidad, interoperabilidad y usabilidad. Las medidas son objetivos verificables para el alcance académico y serán refinadas después de evaluar tácticas y patrones.

| ID | Atributo | Fuente | Estímulo | Artefacto | Entorno | Respuesta | Medida |
|---|---|---|---|---|---|---|---|
| QA-01 | Disponibilidad / Resiliencia | Pérdida de conectividad a Internet | El nodo edge no puede comunicarse con la nube | Sensor Firmware, Edge API y Edge DB | Operación normal en una plantación remota | Continúa la captura, valida las lecturas, evalúa umbrales y mantiene una cola local pendiente | Operación autónoma por al menos 72 horas; 100% de lecturas válidas dentro de la capacidad prevista quedan persistidas localmente |
| QA-02 | Rendimiento | Dispositivo IoT | Envía una lectura que supera un umbral crítico | Edge API, Ingestion Service y Alert Service | Conectividad disponible y carga nominal | Evalúa el umbral, registra el evento y despacha la notificación crítica | Evaluación local <= 2 s; notificación push solicitada a FCM <= 10 s en el percentil 95 desde la recepción en nube |
| QA-03 | Confiabilidad / Integridad | Nodo edge | Reintenta un lote tras una sincronización interrumpida | Ingestion Service y su base de datos | Conexión inestable y entrega al menos una vez | Reconoce cada lectura por identidad, acepta las nuevas e ignora las repetidas sin duplicar efectos | 0 lecturas duplicadas persistidas y 0 alertas duplicadas para la misma lectura en pruebas de reintento |
| QA-04 | Seguridad | Usuario o dispositivo no autorizado | Intenta leer datos de otra suscripción o inyectar telemetría | API Gateway, Identity Service, Edge API y microservicio destino | Operación normal o intento malicioso | Autentica identidad, valida rol, tenant y pertenencia del dispositivo; rechaza y audita | 100% de pruebas de acceso cruzado rechazadas con `401` o `403`; evento de auditoría registrado |
| QA-05 | Rendimiento | Agronomist | Solicita el dashboard consolidado de sus plantaciones | Dashboard Service y su proyección de lectura | Hasta 50 plantaciones asignadas y carga nominal | Responde desde una vista materializada sin consultar sincrónicamente todos los servicios | Tiempo de respuesta <= 3 s en el percentil 95 |
| QA-06 | Escalabilidad | Flota de dispositivos | Aumenta la tasa de telemetría | API Gateway, Ingestion Service, Event Broker y bases de datos | Pico de hasta 1,000 lecturas por minuto | Distribuye carga, aplica backpressure y escala la ingesta sin escalar todos los servicios | Procesa >= 1,000 lecturas/min; backlog drenado en <= 5 min después del pico; sin pérdida confirmada |
| QA-07 | Modificabilidad | Equipo de desarrollo | Cambia reglas de notificación o despliega una nueva versión de Alert Service | Alert Service y contratos de eventos | Plataforma operativa | Despliega el servicio de forma independiente manteniendo contratos compatibles | Cambio desplegable en <= 30 min; ningún redespliegue de otros microservicios; consumidores existentes continúan operativos |
| QA-08 | Interoperabilidad / Resiliencia | Servicio externo | Open-Meteo, Stripe, FCM o la fuente del INIA falla o excede el timeout | Microservicio propietario de la integración | Dependencia externa degradada | Aplica timeout, reintentos limitados y circuito abierto; conserva la función principal o informa estado pendiente | Timeout <= 3 s por intento; máximo 3 intentos; ninguna falla en cascada hacia servicios no dependientes |
| QA-09 | Usabilidad / Accesibilidad | Usuario web o móvil | Cambia idioma o usa tecnología asistiva | Landing Page, Web Application y Mobile Application | Sesión activa | Conserva contexto, presenta textos localizados y expone controles interpretables | Cambio de idioma sin perder la tarea; cumplimiento WCAG 2.1 AA en los flujos críticos evaluados |

### 4.1.2.3. Constraints

Las restricciones siguientes no se evalúan como preferencias. Provienen del enunciado, de la decisión explícita de migrar a microservicios y de acuerdos ya reflejados en el diseño estratégico y los diagramas de arquitectura del reporte nuevo.

|---|---|---|---|---|
| CTS001 | Adoptar microservicios alineados con bounded contexts | Como equipo, debemos implementar un desplegable independiente por cada uno de los siete bounded contexts para sustituir la arquitectura monolítica modular del proyecto original. | Cada bounded context posee servicio, ciclo de despliegue y propiedad de datos propios; ningún servicio accede directamente a la base de datos de otro. | EP008 |
| CTS002 | Integrar productos digitales multicomponente | Como equipo, debemos integrar Landing Page, Web Application, Mobile Application, dispositivos IoT, Edge API y APIs RESTful internas. | Los productos acceden al backend mediante contratos publicados; los CTA del Landing Page dirigen a la aplicación correspondiente a cada segmento. | EP001, EP008, EP009, EP010 |
